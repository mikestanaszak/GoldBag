# 26.3 release review

## Scope and disposition

Reviewed the release changes in `.github/workflows/ci.yml`, `package.json`,
`package-lock.json`, `release.config.mjs`,
`scripts/Prepare-GoldBagRelease.sh`,
`scripts/verification/release.test.mjs`, and
`scripts/verification/PackagedJarVerification.java` at commit `ddf47a8`.

Disposition: **request changes** for the dependency-pinning requirement. The
release flow otherwise has the intended shape: the release job is limited to a
push of `main`, waits for `harness`, `verify`, and `release-tooling`, uses no
npm publishing plugin, and gives only that job `contents: write`. The current
commit is after `v1.1.1` and has the requested `BREAKING CHANGE` footer, so the
first release is analyzed as `2.0.0`.

## Findings

### P1 — GitHub Actions dependencies are not immutably pinned

**File:** `.github/workflows/ci.yml:21,23,37-38,55,58,97,115,118,123`

All Actions dependencies use mutable major tags (`actions/checkout@v4`,
`actions/setup-node@v4`, `actions/setup-java@v4`, and
`actions/upload-artifact@v4`). A tag can move after review; this is especially
material for the release job, which grants the selected action chain a
`GITHUB_TOKEN` with `contents: write`. Pin every `uses:` entry to a full commit
SHA (with a human-readable version comment), and update those SHAs deliberately
when upgrading. Until that is done, the workflow does not meet the stated
secure, pinned-dependency requirement.

### P2 — Release preparation changes the reproducible build timestamp

**File:** `scripts/Prepare-GoldBagRelease.sh:12-14`

`versions-maven-plugin:2.19.1:set` defaults
`updateBuildOutputTimestampPolicy` to `onchange`. Running the preparation script
changed the fixed root-POM timestamp from `2026-09-05T00:00:00Z` to the current
time before building `GoldBag-2.0.0.jar`. Two otherwise identical release runs
therefore produce different JAR bytes and checksums. The CI incremental check
only proves that a second package in the same checkout is stable; it does not
prove release-to-release reproducibility.

If deterministic release assets are required, pass
`-DupdateBuildOutputTimestampPolicy=never` (or restore a deliberate fixed
timestamp after the version update) and add a repeated release-package hash
check. This is a release-quality risk rather than a version/manifest mismatch:
the generated artifact itself did contain POM/module version `2.0.0`,
`plugin.yml` version `2.0.0`, and manifest `Implementation-Version: 2.0.0`.

## Verified behavior

- `bash scripts/Prepare-GoldBagRelease.sh 2.0.0` in an expendable copy (which invokes the pinned `versions-maven-plugin:2.19.1` version update) completed successfully: 69 Maven tests, packaged descriptor/manifest checks, native SQLite, restart persistence, offline validate-only, restore, and source-export preservation all passed.
- `(cd dist && sha256sum -c GoldBag-2.0.0.jar.sha256)` returned `OK` for the generated release asset.
- The release analyzer tests passed: 5 tests, 0 failures. They cover patch, minor, major, no-release, and major precedence. The current `ddf47a8` breaking footer therefore selects major over the earlier feature/fix commits since `v1.1.1`.
- The exact npm package versions are pinned in `package.json`, and the npm lockfile records resolved versions and integrity hashes. No `@semantic-release/npm` plugin or npm publish command is configured. The release asset globs select the versioned shaded JAR and adjacent `.sha256` file.
- The verifier now requires the artifact manifest `Implementation-Version` to equal the filtered `plugin.yml` version. Maven's release preparation updated all reactor parent/module versions in the expendable checkout before packaging.

## Follow-up re-review

The controller applied both findings in the working tree:

- Every `uses:` reference in `.github/workflows/ci.yml` is now pinned to a full
  commit SHA, with comments identifying the reviewed upstream versions:
  checkout `v4.4.0`, setup-node `v4.4.0`, setup-java `v4.9.1`, and
  upload-artifact `v4.6.2`. The same immutable references are used in the
  release job that has `contents: write`.
- `scripts/Prepare-GoldBagRelease.sh` now passes
  `-DupdateBuildOutputTimestampPolicy=never`, preserving the fixed
  `2026-09-05T00:00:00Z` timestamp while updating reactor versions.

The repeat release preparation was run twice in expendable copies using Java
25. Both builds completed the Maven reactor and packaged verifier. The first
JAR hash was
`55dc7ba1a47280a293cb8249cdbf9d57b9e6e80de622583f584e4fdcea121668`; the
second run passed `sha256sum --check` against that hash. The resulting POM still
contains the fixed output timestamp, and the artifact contains
`plugin.yml` version `2.0.0` and manifest `Implementation-Version: 2.0.0`.

The prior P1 and P2 findings are resolved. The release review is clear for the
scoped files, subject to the normal GitHub Actions run and PR review.
